    Overview

    A PDF that calls Qwen via a relay to generate slop stories and displays the result in Adobe Acrobat.

    Working because the PDF spec's supports javascript, and can recieve inputs through form handling.

    this only works on Adobe Acrobat

    This document is Adobe desktop/mac only by nature -- mainly because adobe was the only pdf viewing company that fully implemented the spec :p
    Your mileage may vary if you use something else (email me if you find something else that works!).

    Requirements

    • Adobe Acrobat or Acrobat Reader, on Windows or macOS.
    • A network connection

    Adobe thinks I'm trying to attack you when it realises a request is being sent out. So it'll ask for your permission. Choose Allow -- I won't do anything too bad >:)

    How it works

    Acrobat exposes exactly one network API to an ordinary document: Doc.submitForm(), which posts the form's fields to a URL. Unlike Net.HTTP.request it is not security restricted, and it works in the free Reader outside a browser.

    The trick is the reply. When the server answers with Content-Type: application/vnd.fdf, Acrobat parses the FDF and imports the values into the document that made the request. Out is a form post; back is a form fill. That round trip is the whole mechanism.

    The document script never waits on the model. It fires a submit, and the relay answers in milliseconds with a job id rather than a story:

    Note

    At document level this is the Doc, which is why the script opens with var DOC = this;. Upstream linuxpdf reaches fields through globalThis.getField() — that works in PDFium, but in Acrobat getField is a Doc method and the global does not exist.

    The return channel

    An FDF file is a small container of field names and values. The relay builds one by hand for every reply — three fields, every time:

    Two details in there are load-bearing. There is no /F or /UF key — Adobe's Enhanced Security rules require its absence for a document opened from the local filesystem. And only /Fields injection is used: an FDF can also carry /JavaScript, but Enhanced Security blocks that unless the file sits in a privileged location, so nothing here depends on it.

    Encoding the text

    Model output is full of em dashes and smart quotes, and the field's font is WinAnsi. So the encoder emits a literal string (...) when the text is pure ASCII — keeping the FDF readable while debugging — and a UTF-16BE hex string <feff...> otherwise, where the leading byte-order mark is what identifies it as Unicode.

    Newlines are a trap

    Acrobat's line separator inside a multiline field is a carriage return, and it must be written as the two-character escape \r. A raw CR byte inside a literal string is read by the specification as \n, which silently changes the separator.

    The polling loop

    Acrobat will not hold a submitForm connection open for a slow response. The first working version called the model inline, took 15–35 seconds, and Acrobat dropped the socket before the reply could be written — the relay logged ConnectionResetError: [WinError 10054] after returning 200, and the document showed nothing. There is no timeout setting to raise.

    So the document polls. It re-submits with the job id every four seconds until the status line says the job is done:

    Never read a field straight after submitting

    The FDF reply has not been imported at that point, so you read stale text. The first version scheduled its opening poll only if the status already said WORKING — which it never did that early. So polling never started, and every click silently leaked a new job on the relay while the document ignored the results. The first poll is now scheduled unconditionally, and is_finished() decides when to stop.

    There is also a Poll now button. If app.setTimeOut ever fails to fire in this context, that button still retrieves the result — and it is the quickest way to tell the two failure modes apart. The job field is left visible for the same reason: if this breaks, whether the id survived the FDF import is the first thing to check.

    Why the relay exists

    Two reasons, both unavoidable.

    It holds the key

    Anyone who opens a PDF can read every byte of it, so a key embedded in the document is a published key. The document just asks for a story; the relay holds the credential. The proxy hop is not only a limitation — it is the thing that makes distributing the file safe.

    It answers instantly

    The relay never calls the model from the request handler. It writes a job to Redis, replies with the id, and continues generating after the response has been sent via waitUntil(). Job state lives in Redis rather than memory because Vercel functions are stateless and two polls will not hit the same instance.

    Note

    Errors are shown, not swallowed. A missing key or an upstream failure comes back as an FDF that fills status with the reason, so the document tells you what went wrong instead of sitting blank.

    The model

    The default is qwen/qwen3-32b, measured at 13–20 seconds per story. Speed is the reason for the choice, not quality: a Vercel Hobby function is killed at 60 seconds and waitUntil work dies with it, so anything slower leaves jobs that never finish.

    Reasoning models are a trap here

    They burn 300–900 tokens thinking before writing a word, and take anywhere from 16 seconds to over three minutes for the same prompt. If max_tokens does not cover the thinking as well as the story, the API returns finish_reason: "length" with content: null — no story, no error, nothing. That is why MAX_TOKENS defaults to 3000 rather than the ~500 a 300-word story needs, and why both relays raise a message naming this cause instead of failing on a null.

    Note also that a leading ~ on a model id, as in ~deepseek/deepseek-v4-flash-latest, is part of the id and not a typo — it marks a floating alias on the proxy. Without it the API answers is not a valid model ID.

    The prompt itself is fixed (BASE_PROMPT, defined in both relays — keep the two copies in sync), plus your topic if you typed one, plus a short random entropy token. That token exists because the prompt asks the model to be random, and because it stops any layer in between from serving a cached completion.

    Run it locally

    .env is gitignored. A real environment variable overrides the file, so CI and one-off overrides still work.

    Open out/slop.pdf in Acrobat, optionally type a topic, and click Generate. The dev relay is stdlib-only and serves the same public/ directory Vercel does, so http://127.0.0.1:8000/ shows this very page. Routes are /, /slop.pdf, /crossdomain.xml and POST /api/story. Static files are read off disk per request, so a rebuild needs no restart.

    Keep the two builds straight

    The relay URL is baked in at generation time. A PDF built with local will keep trying 127.0.0.1 on whoever opens it.

    FileTalks toPurpose
    public/slop.pdfhttps://slop.alexvd.dev/api/storyCommitted, deployed
    out/slop.pdfhttp://127.0.0.1:8000/api/storyLocal testing, gitignored

    Use 127.0.0.1, not localhost

    On Windows localhost resolves to ::1 first. With the dev relay bound to IPv4 only, every request pays a ~2 second fallback penalty. The same relay over 127.0.0.1 answers in 3ms.

    Deploying

    The public build runs on Vercel at slop.alexvd.dev.

    1. Add the Upstash Redis (or Vercel KV) integration. It sets KV_REST_API_URL / KV_REST_API_TOKEN; the code also accepts the UPSTASH_REDIS_REST_URL pair.
    2. Set HACKCLUB_AI_KEY in the project's environment variables.
    3. Point the domain at the project.

    Rebuild the PDF after any change to httpdemo.js or gen_http_pdf.py, and commit it. It is a build artefact, but Vercel deploys from git and has no Python toolchain here:

    Check the production branch

    Vercel's production branch defaults to the repository's default branch. Make sure that is the branch this code actually lives on, or the deploy will serve nothing and /api/story will 404.

    What silently breaks it

    The policy file, and its Content-Type

    A PDF opened from disk has no origin, so Acrobat treats every response as cross-domain and drops it unless the host explicitly permits it. Vercel would serve .xml as application/xml; Adobe expects text/x-cross-domain-policy, which is why vercel.json overrides it. Verify after every deploy:

    The Required flag

    /Ff flags are 1-based bit positions, so bit 1 is value 1 and bit 2 is value 2:

    BitValueFlag
    11ReadOnly
    22Required
    134096Multiline
    1765536Pushbutton

    Writing Ff = 2 intending ReadOnly actually marks the field Required, and Acrobat then refuses to submit the form at all — "At least one required field was empty." This is easy to miss because Chrome ignores it entirely: upstream linuxpdf set Ff = 2 on all 310 of its fields and nothing ever complained, since that document never submits a form.

    The missing AcroForm dictionary

    Upstream linuxpdf emits no /AcroForm. Chrome tolerates that and scavenges widgets off the page's /Annots; Acrobat resolves getField() names only through /AcroForm /Fields, so every field was invisible to JavaScript there. Three things bite when fixing it with pdfrw:

    • PdfWriter.addpage() resets writer._trailer, so /AcroForm must be attached after addpage() or it is silently discarded.
    • pdfrw has no boolean type — NeedAppearances=True serialises as True, which is invalid PDF. Use PdfObject("true").
    • Fields must be indirect = True, or pdfrw duplicates each one that appears in both /Annots and /Fields — a log.warning only — producing two widgets sharing one name.

    Generation must fit the time limit

    Vercel Hobby caps an invocation at 60 seconds, and waitUntil work dies with the function. Hence the fast default model and JOB_DEADLINE = 55, which reports a clear error rather than letting the document poll for five minutes.
